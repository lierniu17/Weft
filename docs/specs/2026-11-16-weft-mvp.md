# Weft 第一版（MVP）

> 术语以 [CONTEXT.md](../../CONTEXT.md) 为准；架构约束见 [docs/adr/](../adr/) 0001–0004。

## 问题陈述

人到了一定年纪，认识的人越来越多，关于他们的信息却散落在记忆、聊天记录和零碎备忘里：老张的女儿今年高考吗？小李和小王是怎么认识的？上次聊天他说不吃辣还是不喝酒？我是通过谁认识这位客户的？这些信息记不住，就算记下来，联系人簿和备忘录也只能存孤立的条目，表达不了“谁和谁是什么关系、关系怎么变的、这话是谁说的”，更没法用一句话问出答案。

现有工具要么是填一大堆字段的联系人簿（太累，记不下去），要么是一堆没有结构的笔记（记得下，但查不出来）。

## 解决方案

Weft 让用户像写一句备忘一样随手记下和人有关的事（一条**记录**），系统用大模型从中抽取出人物、事实、关系、感受，生成一份**草稿**给用户过目；用户确认后，这些信息进入用户私有的人际关系图谱。

- 每个**人物**都有一份不断丰富的**画像**：身份、社会角色、性格、喜好与厌恶、生活事件、相处之道、本人的**评价**，以及一段综合描述。
- 每一对人物之间的**关系**会被归纳：是什么关系（可以同时是多种）、怎么认识的、谁介绍的、现在怎么样；每个人对另一个人的**感受**单独记录，并且有方向。
- 每条信息都标明**可信度**（亲历 / 本人说 / 转述 / 推测），并能追溯到来自哪条记录；信息变了，旧信息作为历史保留。
- 用户可以用自然语言**问答**：某人是什么样的人、两人什么关系、我是怎么认识谁的、谁喜欢露营、最近半年认识了谁、我认识的人里做 IT 的有几个——每个回答都带**出处**。
- 用户可以在人物页看到他周围一到两层的关系网，也可以看以本人为中心、可筛选的全景图。

第一版是面向中国大陆的邀请制内测，移动端优先的响应式 Web，用户之间数据完全隔离。

## 用户故事

### 账户

- **US-1** 作为受邀者，我想要用邀请码和账号密码注册，以便进入内测。
- **US-2** 作为用户，我想要登录和退出，以便在不同设备上使用、并保护数据。
- **US-3** 作为新用户，我想要注册后图谱里已经有一个代表“我”的本人，以便马上开始记录我和别人的关系。
- **US-4** 作为用户，我想要注销账户并删除我的全部数据，以便我不想用时数据不留在平台上。
- **US-5** 作为用户，我想要确信别的用户无论如何都看不到我的任何数据，以便放心记录私密的人际信息。

### 录入

- **US-6** 作为用户，我想要用一段自然语言写下一条记录，以便不必填表就能记下和人有关的事。
- **US-7** 作为用户，我想要为记录设置发生日期（默认今天），以便补记以前发生的事。
- **US-8** 作为用户，我想要只把发生日期精确到年或月，以便记录只记得大概时间的事（如“2015 年读大学时认识小李”）。
- **US-9** 作为用户，我想要记录里的“上周末”“去年”这类相对时间按发生日期换算成具体时间，以便时间相关的问答是准的。
- **US-10** 作为用户，我想要查看我写过的全部记录，以便回顾和核对。

### 草稿确认

- **US-11** 作为用户，我想要在提交记录后看到一份草稿，逐条列出将要新增或修改的人物、事实、关系、感受和画像内容，以便在入库前把关。
- **US-12** 作为用户，我想要在草稿里修改或删掉任意一条抽取结果，以便纠正大模型的错误。
- **US-13** 作为用户，我想要系统把有把握的人物自动对上号，只在拿不准时列出候选人让我选，以便少点几下又不认错人。
- **US-14** 作为用户，我想要在草稿里把一个提到的人标成“新人物”，以便记录第一次出现的人。
- **US-15** 作为用户，我想要确认过一次“老张就是张伟”之后，系统以后自动认出“老张”，以便越用越省事。
- **US-16** 作为用户，我想要新信息和旧信息冲突时，草稿明确显示“将从 X 更新为 Y”，并保留旧信息作为历史，以便知道发生了什么变化。
- **US-17** 作为用户，我想要可信度更低的冲突信息被标为待核实而不是覆盖旧信息，以便道听途说不会冲掉我确定知道的事。
- **US-18** 作为用户，我想要系统自动判断每条信息的可信度，并允许我在草稿里修改，以便区分亲历、本人说、转述和推测。
- **US-19** 作为用户，我想要放弃一份草稿，以便丢掉写错或不想入库的记录。
- **US-20** 作为用户，我想要在抽取失败时看到提示并能重试，以便记录不会因为一次失败就丢掉。

### 人物与画像

- **US-21** 作为用户，我想要浏览和按姓名或别名查找我图谱里的人物，以便快速找到某个人。
- **US-22** 作为用户，我想要在一个人物的画像页看到他的身份、社会角色、性格、喜好与厌恶、生活事件、相处之道和我的评价，以便全面了解这个人。
- **US-23** 作为用户，我想要社会角色带时间段，并能看到他以前在哪工作、住在哪，以便了解他的经历。
- **US-24** 作为用户，我想要我的主观评价与客观事实分开显示，以便不把自己的看法当成事实。
- **US-25** 作为用户，我想要画像页有一段大模型生成的综合描述，以便快速了解这个人。
- **US-26** 作为用户，我想要点开画像上的任意一条信息就能看到它的出处和可信度，以便核实。
- **US-27** 作为用户，我想要直接在画像页修改或删除信息，以便纠正小错误而不必专门写一条记录。
- **US-28** 作为用户，我想要直接修改的内容也有出处（一条手动编辑记录），以便所有信息都可追溯。
- **US-29** 作为用户，我想要删除一个人物，并被提示有多少条记录提到他、原文会保留，以便清楚删除的后果。

### 关系与感受

- **US-30** 作为用户，我想要看到两个人物之间的关系：关系类型（可以多种）、认识时间、认识途径、介绍人、当前状态和一段总结，以便了解他们之间的来龙去脉。
- **US-31** 作为用户，我想要看到两个人物之间关系的事实时间线，以便了解关系是怎么变化的。
- **US-32** 作为用户，我想要记录 A 对 B 和 B 对 A 不同的感受（亲密度、好恶、信任，各分档位），以便表达不对称的关系。
- **US-33** 作为用户，我想要看到感受随时间的变化，以便知道两个人从什么时候开始疏远。
- **US-34** 作为用户，我想要关系类型使用内置的两层词表，并保留原话（如“铁哥们”），以便既能准确筛选又不丢细节。
- **US-35** 作为用户，我想要在某个大类下自定义新的小类（如“球友”），以便表达词表没有覆盖的关系。
- **US-36** 作为用户，我想要记录不涉及我的第三方关系，并看到它的可信度，以便了解我身边人之间的关系网。

### 图谱可视化

- **US-37** 作为用户，我想要在人物页看到他周围一到两层的关系图，点击某个人就能跳到他的人物页，以便顺着关系网浏览。
- **US-38** 作为用户，我想要看以本人为中心的全景图，并能按关系类型和亲密度筛选，以便看清我的人际结构。
- **US-39** 作为用户，我想要在手机上也能正常查看和操作这些图，以便随时使用。

### 问答

- **US-40** 作为用户，我想要问“某人是个什么样的人”，以便快速了解他。
- **US-41** 作为用户，我想要问“A 和 B 是什么关系、怎么认识的”，以便弄清两人之间的事。
- **US-42** 作为用户，我想要问“我是怎么认识某人的”“通过谁能认识某人”，以便找到人脉路径。
- **US-43** 作为用户，我想要按条件问“我的大学同学有谁”“谁喜欢露营”，以便筛选出一批人。
- **US-44** 作为用户，我想要问“最近半年认识了谁”“他俩什么时候闹僵的”，以便回答和时间有关的问题。
- **US-45** 作为用户，我想要问“我认识的人里做 IT 的有几个”，以便做简单统计。
- **US-46** 作为用户，我想要每个回答都标出出处（依据哪几条记录、可信度如何），以便判断答案靠不靠得住。
- **US-47** 作为用户，我想要图谱里没有答案时系统直接说不知道，而不是编一个，以便信任它的回答。

### 用量与运营

- **US-48** 作为用户，我想要在超过当天录入或提问上限时看到明确提示，以便知道什么时候能继续用。
- **US-49** 作为管理员，我想要用命令行生成和作废邀请码，以便控制内测人数。
- **US-50** 作为管理员，我想要通过配置调整每人每天的录入和提问上限，以便控制大模型成本。

## 验收标准

### 账户与隔离

- **AC-1** 用有效且未用过的邀请码加账号密码可以注册成功；邀请码无效、已作废或已被使用时注册失败并提示原因；每个邀请码只能注册一个账户。〔覆盖 US-1, US-49〕
  - **怎么验**：后台测试检查邀请码的各种状态和一次性使用；真实页面 BOT-1 实际注册一遍。
- **AC-2** 登录后可访问自己的数据，退出后任何需要登录的页面和接口都被拒绝；密码错误时登录失败且不透露账号是否存在。〔覆盖 US-2〕
  - **怎么验**：后台测试检查会话、未登录访问被拒、错误提示一致；真实页面 BOT-1 覆盖登录和退出。
- **AC-3** 注册成功后，用户图谱里恰好有一个本人，姓名为注册时填写的称呼。〔覆盖 US-3〕
  - **怎么验**：后台测试检查注册后本人存在且唯一；真实页面 BOT-1 在人物列表里看到“我”。
- **AC-4** 用户 A 无法通过任何途径读到、改动或删除用户 B 的数据：直接访问 B 的人物、记录、草稿 ID 返回“不存在”；A 的问答（含路径、筛选、统计）永远不会引用 B 的人物或记录；A 的全景图里不会出现 B 的人物。〔覆盖 US-5〕
  - **怎么验**：后台测试覆盖每一个读写接口与每一个问答查询工具，用两名用户各自造数据后交叉访问；真实页面 BOT-8 用两个账户实际交叉访问一遍。
- **AC-5** 注销账户后，该用户在 Postgres 和 Neo4j 中的全部数据被删除（按该用户的租户范围查询结果为空），账户无法再登录，邀请码不可复用。〔覆盖 US-4〕
  - **怎么验**：后台测试注销后在两个库里按租户范围逐类查询为空；真实页面 BOT-11 注销后尝试登录。

### 录入与时间

- **AC-6** 用户提交一段文字后生成一条记录和一份状态为“抽取中”的草稿；抽取完成后草稿变为“待确认”；空白内容不能提交。〔覆盖 US-6, US-11〕
  - **怎么验**：后台测试检查记录与草稿的状态流转；真实页面 BOT-2 实际提交一条记录。
- **AC-7** 记录的发生日期默认是提交当天，可以改成任意过去的日期，也可以只选到年或月；不能选未来日期。〔覆盖 US-7, US-8〕
  - **怎么验**：组件测试检查日期选择器的三种精度和未来日期不可选；后台测试检查精度被正确保存；真实页面 BOT-12 补记一条精确到年的记录。
- **AC-8** 记录中的相对时间按发生日期换算：发生日期为 2026-11-16 的记录里“上周末”换算为 2026-11-14 至 15；“去年”换算为 2025 年；发生日期只精确到年时，“那年夏天”只换算到年份，不臆造月日。〔覆盖 US-9〕
  - **怎么验**：后台测试用录制好的大模型响应检查换算结果写入事实的时间；抽取质量评测的样例中包含补记和相对时间类别。
- **AC-9** 记录列表按发生日期倒序显示全部记录，每条显示原文、发生日期和草稿状态；点进去能看到这条记录产生了哪些信息。〔覆盖 US-10〕
  - **怎么验**：组件测试检查列表项的各状态；真实页面 BOT-2 在记录列表里看到刚提交的记录。

### 草稿确认

- **AC-10** 草稿按类别分组显示所有将要写入的内容：涉及的人物（含匹配结果）、新增事实、关系变化、感受变化、画像变化；每一条都显示可信度。用户确认之前，图谱中不出现任何草稿里的内容。〔覆盖 US-11, US-18〕
  - **怎么验**：组件测试检查草稿卡片的分组和每条的可信度展示；后台测试检查确认前图谱里查不到草稿内容；真实页面 BOT-2 实际确认一份草稿。
- **AC-11** 用户可以修改草稿中任意一条的内容、关系类型和可信度，也可以删掉某一条；确认后写入的是修改后的内容，被删掉的条目不写入。〔覆盖 US-12, US-18〕
  - **怎么验**：后台测试检查改动和删减后的写入结果；真实页面 BOT-2 在确认前改一条可信度、删一条事实。
- **AC-12** 人物匹配有三种状态：已匹配（直接显示对应人物）、需选择（列出候选人和“这是一个新人物”选项，未选之前不能确认草稿）、新人物。图谱里只有一个“张伟”且记录写“张伟”时应为已匹配；有两个姓张的人物而记录写“老张”时应为需选择。〔覆盖 US-13, US-14〕
  - **怎么验**：组件测试检查三种状态和“未选不能确认”；后台测试用录制好的大模型响应检查两种场景下的匹配状态；真实页面 BOT-3 实际选一次候选人。
- **AC-13** 用户在需选择时把“老张”选为张伟并确认后，“老张”被记为张伟的别名；之后另一条提到“老张”的记录，在图谱里没有其他别名为“老张”的人物时，自动匹配为张伟。〔覆盖 US-15〕
  - **怎么验**：后台测试检查别名写入和下一次的自动匹配；真实页面 BOT-3 连续提交两条记录验证。
- **AC-14** 新信息与已有信息冲突且可信度不低于原信息时，草稿显示“将更新：<旧值> → <新值>”；确认后旧信息被标为截至新记录的发生日期，仍能在画像的历史里看到，并且可以问答查到。〔覆盖 US-16, US-23〕
  - **怎么验**：后台测试检查旧事实被标失效且保留、问答工具能查到历史；真实页面 BOT-4 实际走一遍工作单位从字节更新为阿里。
- **AC-15** 新信息与已有信息冲突且可信度更低（例如已有“本人说在字节”，新记录是“转述在阿里”）时，草稿把它标为待核实；确认后旧信息仍是当前值，新信息以待核实状态显示在画像中。〔覆盖 US-17〕
  - **怎么验**：后台测试检查可信度比较规则和待核实不覆盖；真实页面 BOT-4 覆盖待核实分支。
- **AC-16** 可信度四档的顺序为 亲历 = 本人说 > 转述 > 推测（亲历与本人说同级，冲突时视为不低于）；大模型对每条信息给出初始可信度。〔覆盖 US-18〕
  - **怎么验**：纯函数测试检查可信度比较；抽取质量评测检查可信度判断准确率不低于 0.8。
- **AC-17** 放弃草稿后图谱不发生任何变化，记录保留并标为“已放弃”。〔覆盖 US-19〕
  - **怎么验**：后台测试检查放弃后图谱不变、记录状态；组件测试检查放弃按钮的二次确认。；真实页面 BOT-13 实际放弃一份草稿。
- **AC-18** 抽取失败（大模型超时、返回无法解析）时草稿变为“抽取失败”，页面显示提示和重试按钮，重试成功后进入待确认；记录原文不丢失。〔覆盖 US-20〕
  - **怎么验**：后台测试用模拟的失败响应检查状态和重试；组件测试检查失败态展示。
- **AC-19** 确认草稿是幂等的：同一份草稿重复确认（例如网络重试）只写入一次；写入图谱中途失败时草稿保持待确认，用户可以再次确认，不产生重复的人物或事实。〔覆盖 US-11〕
  - **怎么验**：后台测试模拟重复确认和写入中途失败。

### 人物与画像

- **AC-20** 人物列表显示全部人物（本人置顶），可以按姓名或任一别名查找，输入“老张”能找到别名为老张的张伟。〔覆盖 US-21〕
  - **怎么验**：后台测试检查别名查找；组件测试检查列表和空状态；真实页面 BOT-3 用别名查找。
- **AC-21** 画像页分区显示：基本身份、社会角色、性格、喜好与厌恶、生活事件、相处之道、我的评价、综合描述；没有内容的分区显示空状态，而不是隐藏。〔覆盖 US-22, US-24, US-25〕
  - **怎么验**：组件测试检查各分区和空状态；真实页面 BOT-2 确认草稿后画像页出现对应内容。
- **AC-22** 社会角色每一项显示时间段（开始到结束，或开始至今）；已结束的显示在“历史”里。〔覆盖 US-23〕
  - **怎么验**：组件测试检查时间段与历史分组；真实页面 BOT-4 看到字节进入历史。
- **AC-23** 评价只显示在“我的评价”分区，不会出现在事实类分区里，问答引用评价时明确说明这是“你的评价”。〔覆盖 US-24〕

## 测试决策

### 接缝

已与需求方确认的五层接缝，加一组不进 CI 的质量评测：

1. **前端单元**（vitest，node 环境）：纯函数，例如日期精度的展示文案、可信度比较与文案、筛选条件的序列化。不测组件内部状态。
2. **Story 交互**（Storybook，真实浏览器）：组件三层（basics / composites / business）的各种状态，例如草稿条目的已匹配 / 需选择 / 新人物 / 待核实、出处面板、日期选择器三种精度。只通过用户可见的交互和 DOM 检查结果。
3. **服务层**（pytest，不走 HTTP）：用 Docker 起真实的 Neo4j 和 Postgres；**大模型调用全部用录制好的固定响应回放**，测试结果稳定、不花钱。覆盖抽取→草稿→确认写入、匹配与别名、冲突与待核实、级联删除、问答查询工具、限额。这是数量最多的一层。
4. **路由与契约**（pytest + 真实 Neo4j 和 Postgres，走 HTTP）：鉴权、请求与响应结构、错误码，以及**租户隔离**——两名用户各自造数据后交叉访问每一个接口，这是安全红线，所有读写接口都必须被覆盖。
5. **e2e:bot**（Playwright 跑完整系统，Docker Compose 起全栈）：唯一覆盖前后端对接的一层，执行下方 BOT 用例。大模型调用通过可切换的回放模式使用录制好的响应，保证可重复；stage 环境上用真实大模型跑一轮。

**质量评测**（不进 CI）：抽取质量评测与问答质量评测，调用真实大模型，按 AC-42、AC-36、AC-38 的指标出分，修改提示词、切换模型或升级 Graphiti 时手动运行。

好测试的标准：只测外部行为（接口返回、页面上看得到的东西、库里查得到的数据），不测实现细节（不断言调用了 Graphiti 的哪个内部函数、不断言提示词原文）。仓库目前是空的，没有先例可循；第一批交付时建立的服务层和路由层测试即为后续批次的先例。

## 实现决策

### 整体架构

```
浏览器（React 响应式 Web）
   │ HTTPS / JSON
FastAPI（route → service → repository）
   ├── Postgres：用户、邀请码、记录、草稿、自定义关系小类、用量计数
   ├── Neo4j（经 Graphiti + 自建仓储层）：人物、事实、关系、感受、episode   ← 图谱以它为准
   ├── DeepSeek（抽取、匹配消歧、问答、综合描述）
   └── 通义千问 text-embedding-v4（向量）
```

- 图谱以 Neo4j 为准，Postgres 存其余数据（ADR 0003）。记录与 Graphiti episode 共用同一个 ID。
- 大模型经一层供应商抽象接入，两家均使用 OpenAI 兼容接口（ADR 0002）。
- Graphiti 版本锁定在 0.31.x，关闭默认遥测；不部署 Graphiti 自带的 MCP / REST 服务器（ADR 0001）。

### 租户隔离（安全红线）

- 每个用户对应一个 `group_id`（由用户 ID 派生，满足 Graphiti 的字符约束）。
- 仓储层是访问 Neo4j 的唯一入口；它的每个方法都从当前请求的登录会话取得租户范围，**不接受调用方传入的租户参数**；自建的 Cypher 查询一律带租户条件。
- 调用 Graphiti 搜索时总是显式传入当前用户的 `group_ids`，禁止传 `None`。
- 问答不执行大模型生成的任何查询语句，只能调用固定查询工具。
- Postgres 中所有业务表都带用户 ID，仓储层同样强制注入。

### 图谱数据模型（Neo4j）

- **人物**：Graphiti 实体，自定义实体类型 `Person`。属性：姓名、别名列表、性别、生日（含精度）、籍贯、是否本人。身份类字段的每次修改都记录出处记录 ID。
- **画像的其余维度**都表达为“人物 → 某个实体”的事实，以便跨人查询并保留时序和出处：
  - 社会角色：指向 `Organization` / `School` / `City` 实体，事实类型 `WORKS_AT` / `STUDIED_AT` / `LIVES_IN`，带开始与结束时间。
  - 性格：指向 `Trait` 实体（`HAS_TRAIT`）。
  - 喜好与厌恶：指向 `Interest` 实体（`LIKES` / `DISLIKES`）。
  - 生活事件：指向 `LifeEvent` 实体（`EXPERIENCED`，带发生时间）。
  - 相处之道：指向 `Etiquette` 实体（`HAS_ETIQUETTE`，例如“不要提他前妻”）。
  - 评价：从本人指向该人物的 `OPINION` 事实，类型标记为评价，不与事实类混排。
- **事实**：Graphiti 的事实（EntityEdge），自定义属性带可信度、是否待核实；`episodes` 字段即出处；冲突更新通过设置失效时间实现，不删除旧事实。
- **关系**（ADR 0004）：自建 `Relationship` 节点，一对人物最多一个，连接两个人物。属性：关系类型列表（大类、小类、原话）、认识时间（含精度）、认识途径、当前状态（活跃 / 疏远 / 紧张 / 断联）、总结、可信度（第三方关系）、出处记录 ID 列表；另有一条指向介绍人的连接。每次确认涉及这对人物的草稿时更新。
- **感受**：从一个人物指向另一个人物的 `FEELS` 连接，每次变化新增一条（维度、档位、发生时间、可信度、出处记录 ID）；当前值取每个维度最新的一条。
- **中文检索**：Neo4j 全文索引改用 `cjk` 分词器；中文人名的匹配消歧不依赖 Graphiti 的模糊去重（它只处理英文字母和数字），改由别名精确匹配加大模型判断完成。

### 关系类型词表

- 内置大类五个：亲属、情感、社会、利益、敌对。小类约 40 个，从 PersonGraphDataSet 精简，每个大类下有一个“其他”。词表随代码发布。
- 用户自定义小类存于 Postgres，挂在某个大类下，只对本用户可见；抽取时与内置词表一起提供给大模型。

### 录入与草稿流程

1. 提交记录 → Postgres 写入记录（原文、发生日期、精度）和一份“抽取中”的草稿，扣减当日录入额度。
2. 后台任务调用抽取：基于 Graphiti 的分步抽取能力（实体抽取、实体消歧、事实抽取、事实消歧）加上自建的关系、感受、画像抽取，以记录的发生日期作为参照时间；**不调用一步到位、直接写库的 `add_episode`**。
3. 抽取结果整理成草稿内容（结构化 JSON）存入 Postgres，状态变为“待确认”。草稿形状：

   ```
   Draft {
     persons:  [{id, mention, match: matched|ambiguous|new, person_id?, candidates?[]}]
     facts:    [{id, subject, predicate, object, valid_at?, valid_to?, confidence, conflict?: {old, action: update|unverified}}]
     relationships: [{id, pair, types[], met_at?, origin?, introduced_by?, status?, confidence}]
     feelings: [{id, from, to, dimension, level, confidence}]
     profile:  [{id, person, field, value, confidence}]   // 身份类字段
   }
   ```

   补充约定（实现第 1 批时确定）：每一条都有草稿内稳定的 `id`，前端修改、删除按 `id` 定位；关系带 `confidence`（AC-10、AC-28 需要）；`valid_at` / `valid_to` 为带精度的日期，`valid_to` 可选，用于“上周末”这类时间段（AC-8）；亲属类有方向的关系类型按“pair[0] 是 pair[1] 的 X”理解；本人在草稿中以 `person_id = self` 出现。机器可读的契约是 `apps/api/contracts/draft.schema.json`，与本节冲突时以 schema 为准并回改本节。

4. 用户修改或删减条目、选择候选人后确认 → 服务端校验没有未选的需选择项 → 写入 Neo4j（episode、人物、事实、关系、感受、别名）→ 成功后把草稿标为“已确认”。确认请求携带草稿 ID 作为幂等键；写入时按草稿 ID 判断是否已写过，避免重复。
5. 冲突判断：同一人物同一类单值信息（例如当前工作单位）出现新值时比较可信度（亲历 = 本人说 > 转述 > 推测）：不低于原值则更新（旧值失效），更低则标为待核实。
6. 确认后异步重新生成受影响人物的综合描述。

### 问答

- DeepSeek 工具调用模式。固定查询工具（每个都由服务端注入租户范围）：
  - 查找人物（姓名、别名）
  - 读取画像（含历史和出处）
  - 读取两人关系（关系节点 + 事实时间线 + 两个方向的感受）
  - 人脉路径（两人之间的最短关系链，最多 4 跳）
  - 条件筛选（关系类型、亲密度、实体如学校 / 公司 / 喜好、时间范围）
  - 时间查询（某时间段内新认识的人、某段关系的变化事件）
  - 聚合统计（按条件计数并返回人物列表）
  - 语义检索（Graphiti 混合检索，显式传入当前用户的 `group_ids`）
- 回答结构：一段文字加一组说法，每个说法关联若干出处（记录 ID、可信度）；前端据此渲染出处标记。
- 工具返回为空时，回答必须说明图谱里没有相关信息。
- 每次提问扣减当日问答额度。

### 删除

- 删除人物：在 Neo4j 中按租户范围级联删除该人物、他的全部事实、关系节点、感受、别名，以及只与他相关的实体（例如只有他喜欢的某个爱好）；记录原文保留；记录中对他的提及不再链接到任何人物。本人不可删除。
- 注销账户：删除该用户在 Neo4j（整个 `group_id`）和 Postgres 中的全部数据。

| 账户 | 注册（邀请码）、登录、退出、注销 |
| 记录 | 创建、列表、详情（含产生的信息） |
| 草稿 | 详情、修改条目、确认、放弃、重试抽取 |
| 人物 | 列表与查找、画像、直接编辑画像条目、删除 |
| 关系 | 两人关系详情、编辑 |
| 图 | 某人的局部图（层数）、全景图（筛选条件） |
| 问答 | 提问（返回回答结构） |
| 词表 | 读取内置加自定义小类、新增自定义小类 |
| 用量 | 读取当日剩余额度 |

登录使用服务端会话（httpOnly Cookie）；所有业务接口都要求登录。

### 时间

- 记录的发生日期存为日期加精度（年 / 月 / 日）；事实、关系的认识时间同样带精度。
- 相对时间由大模型以发生日期为参照换算，换算结果的精度不超过发生日期的精度。
- 限额按北京时间自然日计算。

### 运营

- 邀请码命令行：生成、列出、作废。
- 配置项：每日录入上限（默认 50）、每日提问上限（默认 100）、大模型供应商与密钥、回放模式开关（测试用）。

## 补充说明

### 调研结论

- 没有可以直接二次开发的现成产品：Monica 是成熟的个人关系管理系统，但不是图谱、也没有大模型能力，只参考其产品设计；Graphiti 提供时序图谱与抽取能力，作为图谱底座；PersonGraphDataSet 提供关系类型词表的参考。
- Graphiti（0.31.2，2026-10 发布，Apache-2.0，约每月一版）：在 Neo4j 上 `group_id` 只是过滤条件，不传则跨租户；`add_episode` 抽取后直接写库，没有只抽取的模式，草稿流程依赖它的分步内部函数（非稳定接口）；中文名模糊去重无效，全文索引默认无中文分词。

### 风险

- **Graphiti 内部函数不稳定**：升级版本可能破坏草稿流程。缓解：锁定版本；升级前跑服务层测试和抽取质量评测。
- **Neo4j 为准、没有重放兜底**：迁移和升级前必须备份 Neo4j。
- **记录（Postgres）与图谱（Neo4j）没有跨库事务**：通过“先写 Neo4j、成功后标记草稿”和幂等键缓解；仍可能出现图谱已写入而草稿状态未更新的情况，再次确认时按幂等键跳过。
- **抽取质量不达标**：AC-42 是第一版能否上线的硬门槛；不达标时优先调整提示词与词表，必要时让 DeepSeek 与千问对话模型对比打分。
- **两家大模型供应商**：任一家不可用都会影响录入或问答。
- **合规**：不备案的内测必须保持邀请制、小范围。

### 采用默认值的事项（审问中未讨论，spec review 后按默认执行）

- 已确认记录的原文能否再编辑或删除：本 spec 暂定**第一版记录确认后只读**，修改信息通过画像页直接编辑完成。审问中没有讨论到这一点。
- 局部图节点上限 50、人脉路径最多 4 跳、关系状态四档（活跃 / 疏远 / 紧张 / 断联）是我给的默认值，审问中没有讨论到。
