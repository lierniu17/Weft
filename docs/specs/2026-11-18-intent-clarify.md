# Weft · 拿不准时反问澄清

> 术语以 [CONTEXT.md](../../CONTEXT.md) 为准（新增“反问”，修订“无关消息”）；与 [ADR 0005](../adr/0005-intent-routing-replaces-explicit-mode.md) 相容（细化“拿不准”的处理，不推翻）；视觉沿用 [DESIGN.md](../../DESIGN.md)。本 spec 修订[按意图自动分发](2026-11-18-intent-routing.md)的 AC-6 和“不在范围内”里的“多轮追问”：只在拿不准意图时允许追问一轮。

## 问题陈述

系统拿不准一句话是想记还是想查时，现在只会回一句固定的“我没确定你是想记下来还是查询”，再给两个按钮。这句话没有说清楚它到底没确定什么，用户得自己猜，还得多点一下。像“老周那事后来咋样了”“老周最近好像不太顺吧”这种话，问一句具体的就能弄明白。

## 解决方案

拿不准时，系统针对这句话问一个具体问题，并给出最多 3 个候选，例如：

> 你是想记下“老周最近不太顺”，还是想查老周最近怎么样？
> 〔记下：老周最近不太顺〕〔查：老周最近怎么样〕

用户可以点候选，也可以直接打字回答。打字时，系统把原话、反问和回答合在一起理解，再按记录、提问或两者处理。只反问一轮：合起来仍然拿不准，就回到现在的“记下来 / 帮我查”。反问本身不扣额度。

## 用户故事

- **US-1** 作为用户，我想要系统拿不准时问我一个具体的问题，以便我知道它没确定的是什么。
- **US-2** 作为用户，我想要反问下方有几个现成的选项，以便点一下就能继续。
- **US-3** 作为用户，我想要直接打字回答反问，以便像聊天一样说清楚，或者补充原话里没说的信息。
- **US-4** 作为用户，我想要系统把我的回答和原话合在一起理解，以便不用把整句话重说一遍。
- **US-5** 作为用户，我想要系统最多只追问一次，以便不会被反复追问。
- **US-6** 作为用户，我想要反问之后接着说一件无关的新事时，这件事被正常处理，以便反问不会卡住对话。
- **US-7** 作为用户，我想要反问不扣额度、最终处理才按类型扣，以便额度只花在真正的记录和提问上。
- **US-8** 作为用户，我想要刷新页面后反问、选项和处理结果都还在，以便随时接着处理。

## 验收标准

### 反问

- **AC-1** 识别置信度低于阈值时，消息仍为 `chitchat`，标记为拿不准，回应改为针对这句话的具体反问，不再是固定话术；同时给出 1–3 个候选，每个候选写明点了会怎么处理（“记下：…”“查：…”）。识别返回的反问为空或无效时，回落到原来的固定话术，以及“记下来 / 帮我查”。〔覆盖 US-1, US-2〕
  - **怎么验**：后台测试（服务层，大模型回放）检查拿不准时返回反问与候选、反问缺失时的回落、候选数量上限；纯函数测试检查候选的校验与截断。
- **AC-2** 反问和候选由识别那次模型调用一起生成，不增加模型调用次数；置信度达到阈值的消息不带反问。〔覆盖 US-1〕
  - **怎么验**：后台测试统计模型调用次数，并检查达到阈值的消息不带反问。

### 回答反问

- **AC-3** 点击候选：按候选的类型处理原消息。选“记下”时，用原话生成草稿（不用候选里改写的句子）；选“查”时，用候选里的问题作答。处理后，原消息的反问标记为已解决，候选不再显示。〔覆盖 US-2〕
  - **怎么验**：后台测试检查两类候选的处理结果和已解决状态；组件测试检查点击回调与候选隐藏；真实页面 BOT-1。
- **AC-4** 打字回答：如果最近一条拿不准的消息还没解决，并且距它不超过 30 分钟（可配置），下一条消息在识别时带上原话和反问作为上下文。模型判断这条是在回答反问时，按合并后的意思处理：记录的草稿文本是原话加回答合并后的内容，提问的问题是合并后的问题；原消息标记为已解决，处理结果显示在回答消息下方。〔覆盖 US-3, US-4〕
  - **怎么验**：后台测试覆盖“回答后记录”“回答后提问”“补充信息后记录”三种情况，并检查合并文本与已解决状态；真实页面 BOT-2。
- **AC-5** 合并后仍然拿不准时，不再反问，回应为固定话术，并给出“记下来 / 帮我查”。点击后按原话加回答的合并文本处理。〔覆盖 US-5〕
  - **怎么验**：后台测试检查第二轮不会再出现反问，以及回落按钮处理的文本；真实页面 BOT-3。
- **AC-6** 模型判断下一条消息不是在回答反问（例如说了一件新事）时，这条消息按普通消息处理；原消息的反问不再接受打字回答，但候选按钮仍然可以点。〔覆盖 US-6〕
  - **怎么验**：后台测试；真实页面 BOT-3。
- **AC-7** 反问和打字回答都不扣额度，最终按记录、提问或两者扣，规则与现在一致；某类额度用完时，给出该类的额度提示，原消息的反问保持未解决。〔覆盖 US-7〕
  - **怎么验**：后台测试检查各步骤的额度变化和额度用完的情况。

### 还原与纠正

- **AC-8** 刷新页面后，反问、候选、已解决状态和回答消息下的处理结果都能还原。已处理的消息照常显示“改为提问 / 改为记录”，规则同按意图自动分发的 AC-10。〔覆盖 US-8〕
  - **怎么验**：后台测试（接口与契约）检查消息列表返回的反问字段；真实页面 BOT-4。

### 质量

- **AC-9** 新增反问评测（约 30 组“模糊原话 + 反问 + 用户回答”，含回答后记录、回答后提问、补充信息、换话题、仍然含糊、“算了”这几类，分调试集和留出集）。留出集上：合并后意图准确率 ≥ 90%；把“换话题 / 算了 / 仍然含糊”误判为记录的比例 ≤ 5%；是否在回答反问的判断准确率 ≥ 90%。拿不准的原话里，带有效反问的比例 ≥ 90%。原意图评测仍需满足 AC-11 的门槛，用户样例评测不低于当前的 19/20。〔覆盖 US-1, US-4, US-6〕
  - **怎么验**：后台测试（意图与反问评测，调用真实 DeepSeek，不进 CI），结果写进开发完成报告。

## 测试决策

### 接缝

沿用已有接缝，不新增：
1. **纯函数**：候选的校验与截断、“是否等待回答”的判定（最近一条、未解决、30 分钟内）、合并文本。先例：`unit/test_intent.py`。
2. **服务层（大模型回放）**：反问生成、点击候选、打字回答、回落、换话题、额度。这是主要测试层。先例：`service/test_messages.py`，用 `LLMScript.intent()` 扩展出带反问和带上下文的版本。同一条请求只配一种回复（回放文件按请求内容去重）。
3. **路由与契约**：新的候选接口和消息字段，隔离测试自动覆盖新路由。
4. **Story 交互**：反问回应（问题、候选按钮、已解决后隐藏），回落按钮行。
5. **e2e:bot**：下方 BOT，回放模式。

只测外部行为：返回的消息、额度、草稿和回答，不测提示词的措辞。

## 实现决策

- **识别输出扩展**：在识别的结构化输出中增加 `clarify: {question, options: [{label, intent: record|ask|record_ask, question?}]} | null`。提示词要求模型在没把握时给出反问；服务端只在置信度低于阈值时采用。候选最多 3 个，`label` 截断，类型非法的候选丢弃；没有有效候选时回落到固定话术。
- **带上下文的识别**：判断“是否等待回答”的规则是：同一用户最近一条消息是拿不准、未解决，且在 30 分钟内（配置项）。满足时，识别请求带上 `context: {original, clarify_question}`，输出增加 `answers_clarification: bool` 与合并后的 `record_text` / `question`。这一轮的提示词明确要求不再反问。
- **消息持久化**：`messages` 新增 `clarify_json`（反问与候选）、`clarification_of`（回答消息指向原消息，可空）、`clarification_resolved_at`。迁移只加列，不改已有数据。
- **接口**：`MessageOut` 增加 `clarify?: {question, options, resolved}` 与 `clarification_of?`。新增 `POST /api/messages/{id}/clarify {option: int}`：点击候选，返回更新后的原消息。打字回答仍走 `POST /api/messages`。
- **处理规则**：点击“记下”候选时，用原话生成草稿；点击“查”候选时，用候选里的问题作答。打字回答时，用合并后的文本处理，结果挂在回答消息上。回落按钮（“记下来 / 帮我查”）在第二轮作用于“原话＋回答”的合并文本。
- **额度**：同按意图自动分发的规则：反问和识别不扣，最终处理按类型扣，改判不退。
- **前端**：在无关消息的回应位置渲染反问（问题文字、候选文字按钮，沿用低调按钮行的样式），已解决后隐藏候选；打字回答无需特殊入口。
- **评测**：`eval/intent/clarify.jsonl`（约 30 组，调试集 / 留出集切分，seed 42），命令为 `uv run python -m weft.eval clarify`；第一轮“带有效反问的比例”复用拿不准的样例。提示词里的示例为虚构，不取自评测集。

### 开发批次

**批次 1：后端反问、上下文识别与评测**

- Goal：识别输出扩展、反问持久化、候选接口、带上下文的识别与合并处理、回落、换话题、额度；反问评测集、评分脚本和首轮真实分数，原意图评测与用户样例回归。
- 输入：本 spec；ADR 0005；已有的意图识别和消息服务。

- 交接物：接口契约与前端类型；回放文件；评测分数。

**批次 2：前端与端到端**

- Goal：反问回应组件、候选点击、已解决状态、刷新还原；BOT-1 至 BOT-4；原有 INTENT BOT-4 适配新的回应。
- 输入：批次 1 交接物；DESIGN.md；本 spec。
- 验收标准：AC-1、AC-3、AC-8（前端部分）。
- 交接物：可在 stage 运行的完整功能；开发完成报告。

## 不在范围内

- 提问中指代不清时（“那事”、两个同名的人）先查图谱再列候选。
- 记录中关键信息缺失时追问补全（是哪个小李、时间含糊）。
- 第二轮及以后的连续追问；回答之后基于上下文的连续问答。
- 让用户设置等待回答的时长。

## 补充说明

- 风险：模型可能把一条新消息误当成在回答反问。兜底是：等待回答只看最近一条消息，且限 30 分钟内；评测里要单独看“换话题”这一类。
- 提示词变化会改变请求内容，所有意图相关的回放文件都要重新生成；原意图评测要回归。
